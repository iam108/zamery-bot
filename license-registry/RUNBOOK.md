# Автоматическое обновление реестра лицензий

Рабочий обработчик развёрнут отдельным сервисом `license-registry` на Railway. Он читает только группу «Лицензии на алкоголь» через Bot API, сохраняет очередь на Volume `/data`, проверяет наступившие события через API-ФНС и пишет в существующий Google-реестр через техническую учётную запись. Mac, Codex и Telegram Desktop для его работы не нужны.

При `CONTACT_SYNC_ENABLED=true` отдельный цикл каждые 15 минут сопоставляет действующие строки реестра с исходными заявками и карточками клиентов бота замеров. Он заполняет только пустые M/N/O (имя, телефон, Telegram), проверяет ИНН, адрес и единственность действующей записи и подтверждает результат обратным чтением. Совпадения с разными контактами или объектами оставляет на проверку. Запросы API-ФНС для этого не расходуются; обработка лицензий продолжается независимо от подключения базы контактов. Прежние ограничения M/N/O в архиве ниже относятся к локальному пилоту; текущее разрешение пользователя допускает заполнение пустых полей контакта.

Настройка, диагностика и порядок восстановления описаны в [DEPLOY.md](DEPLOY.md). Штатный запуск — `node server.mjs`, `DRY_RUN=false`; проверка `/ready` должна возвращать `200` и `stage: running`. Повторная проверка ожидающих событий назначается на 09:00 по Москве. Подтверждённая запись завершается Google readback и `ack`; старые ответы API остаются в очереди.

Старая локальная автоматизация Codex удалена. Сохранность серверной очереди, журнала и учёта API подтверждена перезапуском Railway. Локальные команды ниже сохранены как история пилота; их не следует запускать параллельно серверу.

Рабочая папка: `/Users/dabro108/Documents/ChatGPT/Ник бот замеры`. Настройки источника и назначения: `license-registry/config.json`. ## Порядок каждого запуска

1. Прочитать config.json, эту инструкцию и `node license-registry/cli.mjs status`. Приватное состояние находится в license-registry/private/state.json. Не читать и не выводить значение ключа; передавать программе только путь из config.json. Не публиковать секрет, не помещать ключ в URL, аргументы команд или отчёт.
2. Через Google Drive MCP прочитать актуальные metadata выбранного spreadsheet. Проверить точный лист «Реестр лицензий», sheetId=0 и заголовки A:Q. Прочитать ограниченный фактическими gridProperties диапазон A1:Q<rowCount>, plain formatted values сохранить как `{values:[...],startRow:1}` в private/context.json (0600). При изменении структуры не писать в другой лист наугад, записать причину и уведомить владельца.
3. Через CUA открыть уже авторизованное приложение `com.tdesktop.Telegram`. Найти именно группу «Лицензии на алкоголь». Не отправлять в группу сообщения. Перед действиями получать свежий AX-снимок, индексы не сохранять между запусками. Кнопка `Search messages` внутри открытой группы запускает поиск только в ней. В Search последовательно выполнить запросы config.sourceQueries. Поиск асинхронный: после ввода дать ему завершиться, подтвердив в AX список результатов нужной группы или явное отсутствие результатов. Не считать пустой снимок сразу после ввода доказательством отсутствия сообщений.
4. Результаты поиска Telegram содержат дату и время, например `text Group, Лицензии на алкоголь, ... 30.10.2026 at 10:51, ID: ...`. Полный AX-снимок каждой выдачи сохранить CUA через Node fs в private/source-<номер>.ax, 0600. Читать все результаты новее текущего курсора с перекрытием 7 дней, но не раньше config.startFrom. Если первый экран не покрывает этот период, прокрутить список результатов до покрытия. Не читать другие группы как источник событий. Даты нельзя угадывать по изображению решения или времени получения файла. Не использовать нативные AX ID как Telegram message_id.
5. Разобрать снимки `node license-registry/telegram-ui.mjs --snapshot <file> --since <ISO> --out <file> --export-messages research/telegram-study-complete/chats/chat-5164597211-39cf076ba725/messages.jsonl`. Проверенные старые сообщения сопоставляются с уже имеющимся JSONL-экспортом; для новых UI-наблюдений используется отдельный стабильный ui-идентификатор, не выдаваемый за настоящий message_id. Объединить полученные messages без повторов в private/messages-current.json. При ошибке даты или неполной выдаче записать проблему, не продвигать курсор. Название организации/ИНН можно дополнить только из точного совпадения с существующей таблицей, предшествующей заявкой или доступным клиентским чатом. Никогда не извлекать ИНН из номера P001.
6. Выполнить `node license-registry/cli.mjs ingest --file <messages-current.json> --context license-registry/private/context.json`. Неизвестные организации и неоднозначные объекты остаются review, о них нужно сообщить, а не пропускать. После сохранения ВСЕХ новых наблюдений продвинуть checkpoint до времени успешно завершённого сканирования. Все ожидания и ошибки остаются в state.json независимо от курсора.
7. Выполнить `node license-registry/cli.mjs due`. Для fetched/planned-задачи продолжить план/запись, не делать повторный API-запрос. Для due waiting-задачи выполнить fetch с job ID, абсолютным путём ключа из config и единым run-id запуска. Команда использует POST, системный прокси и проверенный User-Agent. Соблюдать лимиты 3 запроса за запуск, 10 в сутки и резерв 20. Не опрашивать все 699 организаций. Не выполнять живые API-запросы для already-done событий.
8. При IP/ключевой ошибке остановить API-запросы. Не изменять allowlist, не отключать защиту и не покупать тарифы автоматически. Уведомить владельца о конкретной причине. После восстановления соединения допускается `unblock --reason <проверенная причина>`; неопределённый сетевой тайм-аут приводит к ограниченному повтору, не к потере события.
9. Для каждого fetched-события выполнить `node license-registry/cli.mjs plan --job <id> --context license-registry/private/context.json`. Старый ответ, несколько подходящих объектов, неразрешённая компания или конфликт дат не должны порождать запись. Свертэ — известный пример: сообщение октября, а API пока отдаёт апрельское событие; оно должно оставаться waiting. После 7 безуспешных попыток — review с уведомлением.
10. Перед записью через Google Drive MCP заново найти строку по ИНН, номеру и объекту и прочитать get_spreadsheet_cells целевых ячеек с userEnteredValue, formattedValue, dataValidation, note и форматами. Если row number изменился, обновить context и перепланировать. Не перезаписывать изменения сотрудника. Тип деятельности K принимает только `Общепит `, `Магазин`, `Опт` (в первом значении есть пробел). Даты записывать числовыми датами Google Sheets с существующим DATE-форматом, а не ISO-текстом. ИНН и номер лицензии хранить строками. Допустимы только поля E,G,H,I,J,K,L и P, причём P заполняется только если пусто. A:D,F,M:O,Q принадлежат сотрудникам. Не заменять более точный адрес старым ответом API.
11. Обновление выполнять одним связным batch_update_spreadsheet с минимальным field mask. Если создаётся новая строка, сначала проверить её пустоту во всём A:Q и перенести только формат/валидацию из подходящей строки, не чужие значения/коммерческие поля. В H можно добавить note с датой проверки и источником; сохранять существующие пользовательские notes. Значения нового клиента требуют подтверждённого названия из чата/базы, не придуманного API.
12. После записи перечитать изменённые ячейки и идентифицирующие G/H/I/J. Сохранить private/readback-<job>.json: verified=true, точный planHash, spreadsheetId, sheetName, текущее verifiedAt и cells с фактическими значениями ВСЕХ plan.expectedCells. Затем выполнить ack. Никогда не завершать job только по успешному ответу записи: нужен readback. Noop также требует подтверждения правильной лицензии и дат. При сомнительном результате повторить чтение, не создавать дубль.
13. Коротко уведомлять о подтверждённом изменении таблицы, ошибке доступа, исчерпании квоты или необходимости уточнить организацию/объект. Если нет новых результатов и действий, не публиковать очередной статус. Не отправлять сообщения коллегам, клиентам или поставщику и не менять права доступа.

## Особенности существующей таблицы

Столбец H сейчас скрыт пользователем; номера в нём доступны через API. Не раскрывать и не перестраивать столбцы автоматически. Нативная таблица «Таблица1» имеет tableId 1140602151 и первоначально охватывает A1:Q804, при этом заполненные строки уже продолжаются до 880. При фактическом добавлении новой строки необходимо перепроверить актуальные границы нативной таблицы и включение новой записи в фильтруемую область. Расширение выполняется точечно по актуальному tableId, с сохранением пользовательских значений и форматов; никаких очисток и глобального переоформления. Для получения полной структуры через текущий коннектор при необходимости поддержан возврат updatedSpreadsheet в batch_update с установкой уже существующего заголовка «Реестр лицензий» в то же значение. Не угадывать таблицу или bandedRange ID при изменении структуры владельцем.

До запуска помощника два запроса fsrar уже были использованы при проверке доступа. В состоянии записан подтверждённый baseline=2; ответ stat подтвердил общий лимит 100 и расход 2. Это учитывается при резервировании последующих запросов.
