# Автономный обработчик на Railway

Сервис постоянно получает новые сообщения только группы «Лицензии на алкоголь», сохраняет очередь, утром проверяет наступившие события через API-ФНС и обновляет существующий Google-реестр. Для работы после запуска Mac и приложения на нём не нужны.

## Отдельный сервис в существующем проекте

Создать в текущем Railway project сервис `license-registry` из этого же репозитория. Настройки нового сервиса задаются непосредственно через Railway Dashboard/API:

| Настройка | Значение |
| --- | --- |
| Root Directory | `/license-registry` |
| Configuration | настройки самого сервиса, без Railway Config File |
| Builder | Dockerfile, автоматически найденный в Root Directory |
| Start Command | `node server.mjs` |
| Healthcheck | `/health` |
| Restart Policy | `ALWAYS` |
| Replicas | `1` |
| App Sleep / Serverless | выключено для постоянного polling |
| Region | `iad1` |
| Watch Paths | `/license-registry/**` |

`railway.toml`/`railway.json` для нового сервиса не используются: Config as Code устарел, подключение новых сервисов к нему запрещено. Для ранее подключённых сервисов поддержка заканчивается 1 декабря 2026 года. [Документация Config as Code](https://docs.railway.com/config-as-code).

Infrastructure as Code (`.railway/railway.ts`) управляет целым проектом/окружением. Для этого переноса он не применяется: изменяются только настройки `license-registry`, без перестройки проекта с действующим ботом. [Документация IaC](https://docs.railway.com/infrastructure-as-code).

Корневые `railway.toml`, Dockerfile, start command и миграции обслуживают действующего бота замеров. Для нового сервиса берётся Dockerfile из `/license-registry`, без корневой pre-deploy миграции. Привязать к новому сервису собственный Volume с mount path `/data`; очередь и квитанции должны переживать redeploy. Volume доступен во время запуска контейнера, поэтому создание файлов состояния выполняется при старте, а не в build/pre-deploy. [Документация Volume](https://docs.railway.com/volumes).

## Доступы и переменные

Заполнить Variables только нового сервиса по `.env.example`:

- `BOT_TOKEN` — отдельный бот, добавленный в целевую группу. Ему нужен доступ к обычным сообщениям (отключённый privacy mode либо статус администратора). Токен действующего бота замеров нельзя использовать для второго polling-процесса.
- `TARGET_CHAT_ID` — подписанный числовой ID, подтверждённый методом Bot API `getChat` от имени этого бота. `SOURCE_CHAT_ID=5164597211` сохраняет идентификаторы событий прежней очереди; это ID экспорта, а не автоматически проверенный адрес Bot API.
- `GOOGLE_SERVICE_ACCOUNT_JSON` — секретный JSON отдельного Google service account. Его `client_email` получает Editor только существующего реестра. Открытый доступ «по ссылке» для этого не требуется.
- `FSRAR_API_KEY` — уже полученный ключ API-ФНС; сервер сохраняет его в `FSRAR_KEY_FILE` с правами `0600`. Ключ не помещать в исходники, Docker build args, URL, команды или журналы.
- `STATE_FILE=/data/state.json`, параметры таблицы и расписания — как в примере.
- `DRY_RUN=true` позволяет выполнить проверку без записи Google; после контрольной проверки штатный режим — `DRY_RUN=false`.

В image включается только разрешённый список runtime-файлов. Локальные `private/`, выгрузки Telegram, ключи и тестовые данные исключены `.dockerignore`.

Подтверждённые изменения, ошибки доступа и события, требующие проверки, записываются в структурированные Railway logs. Личные уведомления включаются после настройки и проверки `NOTIFY_CHAT_ID`; до этого сервис ничего не отправляет в Telegram.

При успешном запуске и подтверждённой записи сервер сохраняет приватное событие `state_proof`: SHA-256 очереди и секций jobs/sources/api/telegram/cursors/journal, количество заданий и записей журнала, расход и Telegram offset. До 50 состояний заданий содержат причины ожидания и до трёх номеров лицензий с датами API. Тексты сообщений, контакты, адреса и ключи не выводятся; в Telegram этот снимок не отправляется. Для сравнения после перезапуска из хеша исключены периодические lastIngestAt и runtime.startedAt. Отдельное событие `api_quota` показывает подтверждённый лимит, расход и остаток API-ФНС.

`/health` возвращает HTTP 200, пока процесс работает. `/ready` возвращает 200 только при исправных зависимостях Telegram, Google и API-ФНС и работающем обработчике; иначе — 503 с безопасным кодом ошибки и временем последнего успеха каждой зависимости. Отсутствие успешного polling более 90 секунд или завершённого прохода обработчика более 180 секунд также приводит к 503. Успешный проход обработчика не скрывает отдельную ошибку Telegram. При временной ошибке первоначального подключения сервис повторяет проверку с прежними доступами через 30, 60, 120, 240 секунд, затем не чаще раза в 5 минут. Циклы polling и обработки запускаются только после успешной проверки; повторная инициализация не создаёт второго poller.

## Исходящий IP API-ФНС

Для этого переноса подготовлена поддержка Fixie HTTP/HTTPS `tricycle Free`: 500 запросов и 100 МБ в месяц за $0. В `FSRAR_PROXY_URL` сохраняется секретный proxy URL, в котором балансирующее имя сервера заменено на **один из двух выданных IPv4**. Это официально поддержанный способ работы с одним IP. Только дочерний процесс запросов API-ФНС получает настройки прокси; Telegram и Google работают напрямую. [Тариф Fixie](https://usefixie.com/pricing), [закрепление одного IP](https://devcenter.heroku.com/articles/fixie#connecting-through-a-single-ip-address), [Railway](https://usefixie.com/documentation/railway).

При заданном прокси API-запросы выполняет `api-network-helper.mjs`: Node соединяется непосредственно с числовым IP, открывает HTTP CONNECT и проверяет TLS-сертификат `api-fns.ru` внутри туннеля. Разрешены только POST `/api/stat` и `/api/fsrar`; редиректы запрещены, весь запрос ограничен 20 секундами, ответ — 2 МБ. Авторизация прокси передаётся только при CONNECT, ключ API — только в зашифрованном теле POST. Для HTTPS-прокси дополнительно требуется `FSRAR_PROXY_SERVER_NAME` с исходным именем Fixie; его сертификат также проверяется. Без явно заданного прокси сохранён прежний Python-транспорт с системным маршрутом Mac.

Сначала проверить исходящий адрес через прокси, затем заменить единственную разрешённую привязку ключа API-ФНС на подтверждённый адрес. IP-защита остаётся включённой. После этого проверить `stat` и один реальный запрос `fsrar` с Railway. Само наличие переменной прокси или успешная сборка не подтверждает работоспособность доступа.

Для проверки из контейнера Railway выполнить `node check-egress.mjs` с уже заданной секретной переменной `FSRAR_PROXY_URL`. Диагностика использует тот же транспорт, что API-ФНС, и делает один HTTPS-запрос к ipify через закреплённый прокси; ключ API-ФНС и состояние не читает. В журнал выводятся только `fixie_egress_probe`, исходящий и ожидаемый IP, адрес TCP-подключения и признаки проверки TLS либо безопасный код ошибки. Код выхода `0` означает совпадение адресов, ненулевой — ошибку или другой исходящий IP. До успешной проверки не менять привязку ключа. Сам URL прокси не передавать в аргументах команды.

Текущий ключ API-ФНС ограничен одним разрешённым IP. По актуальной документации Railway статический исходящий адрес доступен на Pro, а современная конфигурация использует три IP с балансировкой. Поэтому включение Static IP само по себе не доказывает совместимость с ограничением API-ФНС. [Документация Railway](https://docs.railway.com/networking/static-outbound-ips).

Перед рабочим запуском проверить фактический тариф, весь набор egress-адресов сервиса и допустимый список у API-ФНС. При несовместимости нужен согласованный доступ для всего набора либо отдельный стабильный egress с одним адресом. Не покупать тариф, не отключать IP-защиту и не расширять allowlist автоматически. Проверка доступности метода `stat` не должна расходовать запросы `fsrar`; затем нужен один контролируемый запрос лицензии из самого Railway.

## Перенос очереди и проверка

1. Передавать существующий `private/state.json` на новый Volume защищённым способом, сохранив выполненные события, расход API, очередь и журнал. Файл не должен попадать в Git, image или публичную ссылку. Сохранить резервную копию. Если сервер уже создал состояние, не заменять его поверх новых событий.
2. Проверить доступ к целевой группе, права бота, Google-заголовки и API. Сообщения других групп обработчик должен игнорировать. Не очищать непринятые Telegram updates при переходе. После добавления бота отдельно дочитать сообщения от последнего локального checkpoint до момента его добавления: Bot API не заменяет экспорт прежней истории. Для пересечения источников предпочтителен свежий JSON-экспорт целевой группы с настоящими message ID; синтетические UI-ID нельзя выдавать за Bot API ID. Вводить полную серверную обработку после сохранения этого промежутка и переноса очереди, сохраняя накопленные updates бота.
3. Для полного контрольного цикла использовать реальное положительное решение: событие сохраняется до подтверждения Telegram, запрос выбирает свежую лицензию, Google получает точечные изменения, обратное чтение подтверждает все ожидаемые ячейки, затем выполняется `ack`.
4. Повторно обработать то же событие: новая строка и повторный запрос не должны появиться. Проверить redeploy и сохранность очереди/курсора на Volume. Старые ответы API остаются ожиданием, неоднозначные организации — проверкой, а не случайной записью.
5. После подтверждения серверного цикла отключить прежнее локальное расписание Codex. Сервер считается автономным только после проверки работы без запущенных приложений на Mac и успешного повторного запуска.

Для разовой проверки чтения через существующее выполненное задание можно задать `ACCEPTANCE_SOURCE_JOB_ID` с его ID. Перед единственным запросом `fsrar` сервер атомарно сохраняет на Volume guard `runtime.acceptance` и учитывает запрос в общей квоте и дневном лимите. Допустим только план `noop` без изменений ячеек: реальное обратное чтение Google проходит проверку `ack` во временном состоянии, а отдельная квитанция сохраняется в `runtime.acceptance`. Исходное DONE-задание, его источники и квитанция сохраняются. Событие `acceptance_verified` появляется только в приватном журнале. Проверка подтверждает живые данные API и чтение/ack; фактическую новую бизнес-запись в Google она не проверяет. Guard запрещает повторный API-запрос после перезапуска, ошибки или потери результата. После проверки очистить флаг, сохранив guard.

Перед публикацией выполнить из этого каталога `npm test`. Локальные тесты и Docker-сборка сами по себе не подтверждают живое подключение Railway, Telegram, Google и API-ФНС.

## Личные уведомления

`NOTIFY_CHAT_ID` — положительный Telegram user ID владельца, который предварительно нажал Start у отдельного бота. Сервер проверяет, что это личный чат. После подтверждённого изменения реестра, ошибки или необходимости уточнения бот отправляет уведомление только этому владельцу. Повторы неизменной ошибки подавляются; очередь неотправленных уведомлений хранится на Volume и повторяется даже после завершения задания. При пустом `NOTIFY_CHAT_ID` остаются только структурированные Railway logs.

Ошибки получения Telegram и сохранения полученных событий различаются по фазам `receive`/`persist`. Краткий сетевой сбой записывается в приватный журнал; уведомление приходит при непрерывном сбое от двух минут, а ошибка сохранения — сразу. После успешного получения и сохранения отправляется восстановление ранее объявленного инцидента. Неотправленное уведомление об этом же сбое заменяется восстановлением. Сбой сохранения или доставки уведомления не останавливает рабочие циклы. Записи состояния одного процесса выполняются по очереди до проверки файловой блокировки; действующая блокировка другого процесса сохраняет защиту.
